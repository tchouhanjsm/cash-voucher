Customer onboarding · standard operating procedure

From a domain name to your first successful login.

A guided launch for a single-property Cash Voucher workspace—then a structured User Acceptance Test (UAT) before the client relies on it for daily cash operations.

01 · Domain & subdomain 02 · Isolated Google backend 03 · Publish & first login 04 · UAT & acceptance

Set up safely

Give this customer their own hostname, Apps Script project, Sheet and receipt/backup folders.

02

Prove first access

Open the real HTTPS link, sign in with a temporary password, change it, then sign in again.

03

Test before handover

Run agreed UAT cases with synthetic data. A green source test is not a live acceptance sign-off.

Use this as a shared walkthrough. “Operator” means the person provisioning and maintaining the service; “Client owner” means the client's nominated administrator. Do not ask the client to access GitHub, Apps Script Editor, raw Sheets or private backup folders.

Joint preparation

01. Prepare before opening any dashboards.

Collect the non-secret facts first. This prevents setup against the wrong domain, Google account or existing customer's data.

01

Ask the client owner for

  • Business/property display name and a short customer code.
  • Domain name (for example, example.com) and who controls its DNS.
  • Nominated owner email and list of initial Manager/Staff users.
  • Who can approve test vouchers and who will sign off UAT.
  • Support contact, working hours and preferred onboarding slot.

The operator must prepare

  • Owner-controlled Google account with two-step verification and recovery access.
  • Access to the approved source and static host; only publish the generated dist/ folder.
  • A unique customer Sheet, Apps Script deployment, Drive receipt/backup folders and site origin.
  • A private instance register for IDs, build SHA, links and test evidence.
  • A plan for synthetic UAT data, rollback/fallback and support escalation.
!
Readiness gate: the repository currently is public. Before a proprietary customer handover, the operator must confirm an approved source-hosting/privacy arrangement and ensure the hosting integration will still build. Do not give a client source-repository access, and do not assume a later visibility change can recall existing public clones.
×
Never reuse: the root config.js endpoint, another customer's Sheet, Apps Script project, Drive folders, host origin, owner password or user accounts.
Operator + domain owner

02. Give this customer a dedicated subdomain.

Example: the client's existing website stays at example.com; the Cash Voucher app lives at vouchers.example.com.

02
A

Choose a hostname

Agree the exact subdomain, such as vouchers.example.com. Use a distinct hostname for each customer. Record who owns and renews the domain.

B

Create the dedicated Pages project

Operator creates a separate Cloudflare Pages project for this customer and records its generated project-name.pages.dev hostname. The project can exist before the backend is ready; complete the first successful customer build in Step 04 before activating the custom domain.

C

Plan the custom-domain association

After Step 04 produces a successful deployment, return to Pages → customer's project → Custom domains → Set up a domain. Enter the agreed hostname and follow the dashboard's verification flow before depending on its CNAME.

Then create the DNS record at the authoritative DNS provider

If DNS is in cPanel / GoDaddy / another DNS host
  1. Sign in to the system that actually manages the domain's DNS zone.
  2. Open DNS Zone Editor / Manage DNS / DNS Records.
  3. Add a CNAME record. Host/Name: vouchers (or the exact format the provider asks for).
  4. Target/Value: the exact project-name.pages.dev target confirmed in Pages. TTL: Auto/Default.
  5. Save. Do not add an A record to an invented IP address.
If Cloudflare manages the DNS zone
  1. Complete the Pages custom-domain setup above.
  2. Follow the dashboard's DNS instructions; the CNAME may be added automatically.
  3. Wait for DNS and certificate activation.
  4. Test https://vouchers.example.com in a private browser window.
!
Beginner pitfall: a DNS subdomain is not necessarily a folder or website created in cPanel. Change records at the authoritative DNS provider. For a Pages custom domain, associate the domain in Pages before relying on the CNAME. Do not change the root domain's nameservers just to add one subdomain.

If the client does not own a domain or cannot change DNS, use the dedicated Pages hostname as the agreed client URL until a custom domain is approved. The project/origin must still be unique to that customer.

Operator only · never share credentials

03. Create the customer's private data backend.

Every client gets a fresh Google Sheet and a bound Apps Script project. This is a separate task from publishing the website.

03
1

Use the operator-controlled Google account

Confirm two-step verification and recovery access. Create a new Sheet named for the customer. From that Sheet choose Extensions → Apps Script so the script is bound to the correct spreadsheet.

2

Prepare the approved code locally

Use a clean checkout of the approved commit. The repository expects Node 20 from .nvmrc.

npm ci
npm run check
npm run test:e2e
3

Bind Clasp to the new Script ID

Prepare a local, ignored .clasp.json with the actual project ID from Apps Script. Never commit this file or OAuth credentials.

{
  "scriptId": "<confirmed-new-customer-script-id>",
  "rootDir": "backend",
  "fileExtension": "gs"
}

Run npx clasp status and npx clasp deployments. Independently confirm the identity before npx clasp push. The backend is split across backend/*.gs; do not upload only a guessed Code.gs.

4

Set the temporary owner properties

Apps Script → Project Settings → Script properties: set OWNER_EMAIL to the nominated client owner, OWNER_PASSWORD to a privately generated temporary password, and optionally OWNER_NAME. Never paste a password into this runbook, a source file or a public issue.

5

Initialize this empty customer project once

Run setup() one time only against the verified new, empty Sheet-bound project. Approve the requested scopes. Confirm expected tabs, private receipt/backup folders and the scheduled backup trigger exist. Confirm every resource belongs to this instance.

6

Create a versioned Web App deployment

Apps Script → Deploy → New deployment → Web app. Use the intended operator execution identity and the access setting required by the static app (the client shell cannot rely on the visitor's Google sign-in). App login and server-side authorization must still protect every action. Record the exact /exec URL privately.

×
Stop immediately if any Script, Sheet or Drive ID matches another client or production unexpectedly. Never run setup() as a routine repair on a populated instance. This guide does not authorize a production migration or deployment.
Operator only

04. Build a separate frontend for this client.

The browser stores offline queues and local state by origin. Different URL paths on the same hostname do not provide customer isolation.

04
Cloudflare Pages · one project per customer

Connect the approved source

  1. In Cloudflare, open Workers & Pages → Create → Pages, then connect the approved Git repository.
  2. Use the approved production branch, normally main.
  3. Set the project to use Node 20, matching repository .nvmrc.
  4. Ensure the hosting integration can access the source after the repository's privacy cutover. Do not enable client access to the repository.
Build configuration

Enter these exact values

Build command

npm ci && npm run build:web

Build output directory

dist

Production environment variable

CV_API_URL=https://script.google.com/macros/s/<this-customer-deployment-id>/exec
  • Paste the exact HTTPS Web App URL created for this customer. It must match the expected Apps Script /macros/s/.../exec format.
  • Save production build settings and deploy. The builder fails closed if CV_API_URL is missing or malformed.
  • Publish only dist/; never publish the repository root, backend/, tests, docs or developer metadata.
  • Confirm the generated frontend config points to this customer's API, not the existing root config.js endpoint.
  • Return to Step 02: associate the custom domain in Pages, then create/verify the CNAME at the authoritative DNS provider. Wait for DNS and HTTPS certificate activation.
  • Check the deployed commit and build logs; keep the source SHA and release date in the private instance register.
!
Separate is separate: each customer requires a new Apps Script project/deployment, Sheet, receipt folder, backup folder and distinct static hostname/origin. Do not use one Pages hostname with customer paths or query parameters as a tenant boundary.
Operator verification

05. Verify the real link—not just the build status.

A successful build proves only that files were produced. It does not prove that DNS, security headers or the correct live backend are in use.

05

Domain and browser check

  • Open the agreed https://... client URL on a clean browser/device.
  • Confirm the certificate is valid and there is no DNS, redirect or mixed-content warning.
  • Confirm the Pages dashboard lists the custom domain as active.
  • Check a second network/device if DNS propagation is still in progress.

Network and security check

  • Open browser Developer Tools → Network. Confirm API requests use this customer's Apps Script deployment.
  • Inspect the main document's response headers: Content-Security-Policy including frame-ancestors 'none', X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy and Permissions-Policy.
  • Check Console for failed requests, blocked resources and CSP violations.
  • Confirm no private source/backend files are exposed by the host.
×
No first-login invitation yet if the app targets the wrong API URL, headers are missing, authentication bypass is possible, or the selected Sheet/deployment identity has not been checked. A generated _headers file alone does not prove the host applied those headers.

Record privately before moving on

Customer code · final HTTPS URL · Apps Script project/deployment identity · Sheet and Drive folder identities · deployed source SHA · build/deploy time · evidence link for the header and API checks.

Record links/IDs in the private operator register only. Never put passwords, OAuth JSON or reusable credentials in the register.

Operator + client owner

06. First login: use the actual client URL.

Do this together during the handover. The account is not ready until the owner replaces the temporary password and confirms a fresh login.

06
1

Deliver the access details safely

Operator gives the owner the final HTTPS application URL and registered email address. Send the temporary password through a separate approved channel. Do not put it in this page, email thread, shared spreadsheet or GitHub.

2

Open and sign in

Client owner opens the application link, verifies the hostname and enters the registered email plus temporary password. A login prompt is expected; the browser should not need direct access to the underlying Sheet or Apps Script editor.

3

Complete the forced password change

Follow the in-app change-password screen and choose a private password between 8 and 128 characters that meets the app's current validation. Do not reuse another staff member's password. The operator must not ask to see or retain the new password.

4

Sign out and sign in again

Confirm that the new password works in a fresh sign-in. Verify the expected landing screen loads and the owner can access only owner-authorized functions. Record only pass/fail, date and evidence reference—not the password.

✓
First-login exit criteria: owner successfully signs in, completes password change, signs out and back in, reaches the correct customer workspace, and the operator can prove the site is talking to the correct customer backend.
!
Do not work around an error by changing the root API URL, sharing an administrator account, disabling authentication or granting direct Sheet access. Stop and correct the target/credential setup privately.
Client owner + operator

07. Create individual users; verify the boundaries.

Never use a shared staff login. The interface may hide actions, but backend authorization must enforce the same permissions.

07
O

Owner

Manages users and application settings, and can review the owner-only audit log. Keep this access limited to the nominated owner.

M

Manager

Handles operational workflows such as viewing property entries, editing/cancelling within policy, approvals and vendor administration.

S

Staff / Accountant

Staff access should be limited to the permitted entry/workflow scope. If the Accountant role is enabled, confirm its report-only boundary in the live permission matrix.

  • Create each account with the user's unique email and a separate temporary password; deliver each person's credential privately.
  • Have each user complete their own password change and first sign-in.
  • Test one allowed action and one denied action for every role against the real deployment.
  • Confirm staff cannot manage users/settings, read the owner-only audit log, or perform manager/owner actions through direct requests.
  • Confirm one user cannot access another customer's records or receipt assets. Never test isolation by putting two clients on the same origin.
!
High-value payment rule: a new PAYMENT of INR 10,000 or more requires separate approval; the creator cannot approve their own payment. Pending approval must remain outside approved totals and cash close until an authorized second person approves it.

Use the current product's implemented permissions and approved policy. Do not invent a role or give broader access merely to make a test pass.

UAT kickoff · client sign-off required

08. Define UAT before testing business workflows.

User Acceptance Testing answers: “Can the intended people complete the agreed work, with the right numbers, permissions and recovery behavior?”

08

Agree at the kickoff meeting

  • Client/property name, UAT dates and session owners.
  • Named testers for Owner, Manager and Staff roles.
  • Browser, phone/tablet models, printer and connectivity to test.
  • Whether an isolated staging workspace is used; confirm its URL and resource identity.
  • Who records defects, severity, retest evidence and final approval.

Set up safe test data

  • Use only synthetic names, vendors, notes, receipts and amounts in staging/UAT.
  • Agree a test prefix such as UAT-CLIENTCODE- in notes/reference fields where supported.
  • Record expected totals before creating vouchers.
  • Mark which test entries will be approved, cancelled and reconciled.
  • Keep a controlled fallback process and preserve test evidence.

What counts as a defect?

Critical / stop

Cross-customer data exposure, unauthorized write/approval, incorrect financial totals, missing/duplicate voucher, lost offline entry or no recoverable backup.

Major

A core workflow, role restriction, report, receipt, or cash-close check cannot be completed and no approved safe workaround exists.

Minor

Non-blocking copy, spacing or usability issue that does not change data, access, amounts or control outcomes. Record an owner and due date.

×
Test in staging, not a live cash book. Do not create or cancel synthetic vouchers in production merely to satisfy UAT. Do not run setup() on an existing populated Sheet. If a dedicated staging environment is not available, pause transactional UAT and provision one first.

Release decision

10. Decide pass, pause or reject with evidence.

The launch is accepted only when the live checks prove correct isolation, access, financial behavior and recovery. Never use “CI passed” as client sign-off.

10

Pass / Fail

Pass / Fail

Immediate stop / no-go: wrong customer data target; unauthorized access succeeds; missing or duplicate voucher; incorrect approved totals; failed/incomplete backup or restore; a pending offline entry is unaccounted for; an unexplained cash variance; or a critical security/header issue. Reference desk

11. Troubleshoot without weakening security.

Identify the failed layer first. Never fix a setup issue by disabling authentication, reusing another endpoint or giving direct access to the data store.
