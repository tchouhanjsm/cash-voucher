# PR #62 — Offline sync and idempotency assurance

## Outcome

Protect voucher integrity when offline synchronization retries, a server commit succeeds but its response is lost, two tabs contend for the same outbox item, or an abandoned tab leaves an expired lease.

## Acceptance criteria

- [x] Verify PR #61 is merged and base this phase on its actual merge commit.
- [x] Preserve the existing voucher schema and public API shape.
- [x] Treat a repeated ClientID with matching normalized voucher details as an idempotent retry.
- [x] Reject a ClientID reused with changed date, counterparty, amount, category, notes or type using a visible `CONFLICT`.
- [x] Do not create additional receipt files for a matching retry or changed-payload conflict.
- [x] Extend backend tests for same-user changed-payload conflict and preserve cross-user ClientID isolation.
- [x] Extend browser E2E to simulate an expired `sending` lease and verify it can be reclaimed on reconnect.
- [x] Preserve existing commit-then-lost-response, recovery import, and two-tab single-submit scenarios.
- Verification evidence is maintained in the live PR description; record CI and Browser E2E links only after both pass against the same final head SHA.

## What changed

- `backend/Code.gs`: compare a previously stored voucher's normalized business payload before treating an existing ClientID as an idempotent retry. Changed details fail with `CONFLICT` instead of returning an unrelated existing voucher as success.
- `test/test-backend.js`: verify a matching retry returns the original voucher without adding receipt files; verify changed financial details are rejected; preserve cross-user ID collision protection; align same-request duplicate fixture with truly identical content.
- `test/e2e.py`: seed an expired IndexedDB `sending` lease left by an abandoned tab before reconnecting. Existing E2E covers a server-accepted request whose response is dropped, recovery import, and two tabs submitting a single create request.
- `docs/HANDOFF.md`, `docs/PRODUCT-ROADMAP.md`, `docs/PR-HANDOFFS.md`, `docs/pr-handoffs/PR-61.md`: reconcile PR #61 merge and the current phase.
- `docs/pr-handoffs/PR-62.md`: this phase handoff.

## Security, failure and finance integrity review

- Server-side authorization and the ScriptLock around writes remain authoritative.
- A ClientID belonging to a voucher the caller cannot see still returns `CONFLICT` without disclosing the existing voucher.
- A matching retry does not rewrite an existing voucher or create another receipt file.
- Receipt attachment bytes are not part of the duplicate-payload comparison. A retry with unchanged voucher fields but changed receipt-only content can still be treated as matching; an immutable request fingerprint would be needed to cover attachment content.
- Reusing a ClientID with changed business details is rejected before new receipt files or voucher rows are committed.
- A timeout or lost response remains ambiguous until retry/reconciliation; client-local pending state must not be described as server-confirmed.
- Existing browser tests use the local mock service. They do not prove live Apps Script, Google Sheets/Drive, device storage eviction, or real concurrent Apps Script behavior.

## Verification

- Local `npm run check`, `npm run test:e2e`, and `git diff --check` were not run from this connector-only environment.
- CI and Browser E2E status/URLs must be recorded in the live PR description after the workflows complete against the exact same final head SHA.

## Residual risks / not verified

- The existing voucher schema does not persist an immutable request fingerprint. This phase compares the stored business fields, so a voucher edited after creation can cause a later retry of its original payload to surface as a conflict; do not silently clear that pending record. A durable immutable idempotency ledger/fingerprint would need a separate schema/migration and backup decision.
- IndexedDB lease behavior is tested in browser automation, not across every browser/device or storage-eviction scenario.
- Live Google auth, real Apps Script lock contention, backup/restore and external accountant import remain unverified.
- A witnessed backup/restore drill into a separate recovery destination remains an operational P0.
